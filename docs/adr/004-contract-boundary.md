# ADR 004：契约边界——以前端实际消费为界

- 状态：已接受
- 日期：2026-11-14
- 关联：[rewrite-plan.md P9/P10/P14](../rewrite-plan.md)

## 背景

旧版有两份 OpenAPI（`admin.openapi.json`、`user.openapi.json`）与 73 个序列化契约测试（锁定 Go DTO 的 JSON 字段名/类型）。重写初期曾把「与 Go 版逐字节兼容」作为默认基线，被明确否定：项目从未部署，没有线上消费者；前端两个项目都在本仓库内、随新版一起重新打包；已发布小程序包不存在。逐字节兼容只会把旧版 DTO 的历史包袱（双字段冗余、两种分页风格并存）原样搬进新版。

## 决策

1. **保留**：URL 路径风格（`/api/v1/user/*`、`/api/v1/admin/*`、`/api/v1/public/*`）、HTTP 信封 `{code, message, data, request_id}`、错误码体系（1xxx 凭证 / 2xxx 冲突 / 5xxx 故障）、JWT 双 kind 与刷新令牌协议、bcrypt 口令哈希。
2. **冻结**：微信支付回调路径 `/api/v1/public/payments/wechat/callback` 逐字符不变（商户平台配置依赖）。
3. **修剪**：响应字段以「前端实际消费审计」为界——审计两个前端对每个响应字段的读取点，删掉零消费字段，输出《字段消费审计表》（阶段 0 产出）；分页/排序/时间格式统一为一套约定（消除 `after_id` 游标与页码并存）。
4. **重建验收基准**：新版 OpenAPI 在阶段 0 生成并冻结，作为契约测试（serde 序列化断言 + OpenAPI 路由快照）的唯一基准；旧版 73 个契约测试**不照搬**。
5. **差分对照收窄**：旧版测试资产只对**资金语义纯函数**做差分（计费、退款、卡扣：同一批输入分别跑新旧两版比输出），其余域不做逐测试翻译。

## 理由

- 契约的真正约束方是本仓库内的两个前端与微信支付平台；前者可同步改，后者只需路径与签名语义稳定。
- 把「兼容旧版 DTO」的验收成本换成「字段审计 + 新 OpenAPI 基准」，一次性消除冗余字段，此后契约演进有单一事实源。

## 后果

**正面**：DTO 干净、契约测试有明确基准、前端请求封装一次改造到位。

**负面与对策**：
- 前端需同步回归（修剪字段 + 分页统一）→ 审计表即前端改动清单，随阶段 8 打包收敛一次性回归；admin-web 与 H5 的请求封装（401 刷新重放）逻辑不变。
- 修剪过度可能误删「将来要用」的字段 → 审计表保留「零消费但语义必要」字段的白名单机制，逐条注明保留理由。

## 被否掉的替代方案

- **逐字节兼容 Go 版响应**：为不存在的消费者付永久成本；旧版 DTO 冗余与双分页风格固化进新版。
- **自由重设计（RESTful problem+json 等）**：信封风格本身不是缺陷，前端全链路依赖它；重设计收益低于全前端重写验证成本。
