# ADR 003：号段模式 ID 分配

- 状态：已接受
- 日期：2026-11-14
- 关联：[rewrite-plan.md P3](../rewrite-plan.md)

## 背景

旧版 ID 生成：`central_db.snowflake_state` 单行持久化（41 位时间戳 + 10 位节点固定 0 + 12 位序列），每次分配都在业务事务里对该行 `SELECT ... FOR UPDATE`。两个问题：

1. **全局串行热点**：所有业务事务在 ID 分配点排队，事务越长堆积越重。
2. 设计上为「多进程并行分配」而设（节点位），新版单体是单实例单写者，多节点语义多余。

## 决策

采用**号段模式**：

- 进程启动时从数据库读取水位，内存中按号段（默认一次 500 个）分配；号段用尽前异步持久化下一水位。
- 持久化采用 `UPDATE ... WHERE 水位 = 旧值` 的 CAS，防多写者（防御性保留，正常仅单实例）。
- **资金场景选项**：需要「ID 与业务记录同事务提交、崩溃不跳号可见」的写入（如订单号），支持在业务事务内同步取号并提交水位的强一致路径；普通场景（日志型、可重试型记录）走内存号段。
- 语义保留：bigint、按时间趋势递增；崩溃丢弃未用号段可接受（ID 只要求唯一与趋势有序，不要求连续）。

## 理由

- 消除唯一的全局锁热点；配合 1000 并发充电下异订单并行、同订单串行的锁模型，系统内不再有全局串行点。
- 实现简单（约百行），不引入新依赖。

## 后果

**正面**：热点消除；分配路径从「每次一个 DB 行锁事务」变为内存操作。

**负面与对策**：
- 崩溃丢失号段造成 ID 空洞 → 接受（记录主键本就允许空洞）；台账对账不依赖 ID 连续性。
- 时钟回拨不再需要处理（不再混用时间戳位），但水位持久化失败时必须拒绝发号（fail-fast）→ 实现：号段耗尽且水位未落库时阻塞等待，不得静默重用。
- 水位表成为新的写点（每个号段一次）→ 频率约 `业务写入速率 / 500`，按预算（事件峰值 ≈ 0.17 单/秒）可忽略。

## 被否掉的替代方案

- **UUIDv7 / 字符串 ID**：改列类型波及全部 84 张表与索引，收益仅是去中心化发号——单实例下无意义。
- **保留行锁雪花**：热点照旧，仅删除多节点位，改动收益不成比例。
- **数据库自增列**：分库时代遗留的批量取号/预生成 ID 场景（先拿 ID 再落多表）不便，且暴露连续性给外部（订单号可被猜测枚举）。
