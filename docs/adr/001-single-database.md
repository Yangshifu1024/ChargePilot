# ADR 001：单库合并

- 状态：已接受
- 日期：2026-11-14
- 关联：[rewrite-plan.md P1/P2/P7](../rewrite-plan.md)

## 背景

旧版按「部署进程」切分了三个 MySQL 库：`central_db`（71 张表，几乎全部业务）、`gateway_db`（16 张表，设备运行时）、`worker_db`（2 张表，调度框架）。逐项核实：

- 三库之间**没有任何跨库 JOIN 或跨库事务**——分离没有换来任何数据层语义，只留下了进程边界的影子。
- 三库 89 张表中**唯一重名的是 `event_outbox`**（central 与 gateway 各一张，同构；central 里还有按来源分的 `admin_event_outbox`，共三张同构表）。
- `worker_db` 的调度框架（`scheduled_task` + `task_execution_log`，含租约 CAS、崩溃恢复、连续失败自动暂停）处理器登记表为空，唯一种子任务 `webhook_dispatch` 在代码中零引用——为不存在的需求建的基建。
- 项目从未部署，无数据兼容约束。

## 决策

1. 合并为**单 database、单连接池**；三张同构 outbox 表合并为一张（加 `source` 列区分 user/admin/gateway 来源）。
2. 删除 `worker_db` 全部 2 张表与整套 DB 调度框架（固定周期任务改用 tokio task，运行观测走 metrics + admin 诊断接口）。
3. 删除 `sync_delivery_retry` 表（跨进程投递失败退避机制），由进程内重试 + 命令表 `next_retry_at` 字段承担。
4. 合并后约 84 张表，逐表标注所属模块；模块→表归属清单作为阶段 0 产出并随代码维护。

## 理由

- 库边界等于进程边界，是部署拓扑渗入数据模型的产物，单体化后失去存在理由。
- 单库使此前「跨进程只能最终一致」的流程获得同库事务能力（如写命令 + 推进订单状态同事务），直接支撑 P5/P7 的流程塌缩。
- 部署少 2 个库账号、2 份迁移、2 份连接配置。

## 后果

**正面**：事务塌缩、运维简化、连接池收敛、迁移器只需处理一个库。

**负面与对策**：
- 失去库级写权限隔离，模块越界写表只能靠纪律 → 用 crate 依赖方向强制 + 表归属清单评审；repo 层表名集中在各域 `*_repo` 文件，评审可 grep。
- 表合并后的历史 SQL 参考价值下降 → 旧版迁移 SQL 仅作列定义参考，新版 schema 以阶段 0 设计稿为准。

## 被否掉的替代方案

- **保留三库（单实例三 database、三连接池）**：迁移 SQL 零改动、最保守；但永久保留两份无意义的事务边界，流程塌缩（P7）做不彻底，且「数据兼容」前提不成立（从未部署）。作为新版稳定后的可选优化重新评估，不作为起点。

## 修订记录

- **2026-11-14（阶段 03）**：设备导入与开通（provision）塌缩为同一业务事务。原「device 域受理 → HTTP → gateway 开通」在单体中跨进程消失，`device_provision`/`device`/`device_port` 的导入写入并入 device 模块事务；gateway-runtime 保留连接会话/遥测/命令表的独占写。表归属清单中这三张表的「gateway-runtime 独占写」标注据此修订为「device 域导入事务写，gateway-runtime 运行时读」。
