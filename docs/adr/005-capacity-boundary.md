# ADR 005：容量与可用性边界

- 状态：已接受
- 日期：2026-11-14
- 关联：[rewrite-plan.md G1–G7 及第八节](../rewrite-plan.md)

## 背景

新版硬性容量目标：**至少 2000 台设备同时连接（TCP），至少 1000 台同时充电**。协议参数（DC589 5.8.9 + 旧版实现）：空闲心跳 60s、充电中心跳 15s、端口数据随心跳附带、注册 A0 每 3s×10 次重试（其后 5s）、帧最大 257 字节。项目从未部署，容量设计没有历史数据可依，全部由预算推导。

## 决策

### 负载预算（设计依据）

| 负载项 | 推导 | 结果 |
|---|---|---|
| 帧接收速率 | 空闲 2000÷60s + 充电 1000÷15s | ≈ 83 帧/秒 |
| 心跳状态更新 | 2000÷60s | ≈ 33 UPDATE/秒 |
| 遥测明细写入 | 1000×15s | ≈ 67 INSERT/秒 |
| 聚合 UPSERT | 15min 桶 × 1000 端口 | ≈ 1.1/秒 |
| 订单事件峰值 | 高峰 100 台/10min | ≈ 0.17 单/秒 |
| 实时估费读 | 30% 在线 × 10s 轮询 | ≈ 30 QPS |

结论：吞吐余量约三个数量级，真正的工程对象是连接治理、写放大、重连风暴、背压与可观测性。

### 设计约束（G1–G7，详见 rewrite-plan 第四节）

- 单实例设计；每连接独立 task、读超时 90s、同设备互踢、accept 限速 200 连接/秒。
- 遥测**分级语义**：会话内存快照（不可丢，实时读的数据源）＞聚合表（可由明细/心跳重算）＞明细表（可丢，崩溃损失窗口 ≤200ms）。
- 遥测批量落库：有界缓冲 4096，每 200ms 或满 500 条批量 INSERT；缓冲满丢最旧明细并计数。
- 命令下发走有界队列（深度 16），慢消费者落 `next_retry_at` 退避。
- 观测指标（连接数/充电数/帧速率/缓冲深度与丢弃计数/事件投递延迟/兜底滞后）在阶段 1 内置，容量验收以指标实测为准。

### 容量验收标准（硬性）

| 指标 | 目标 |
|---|---|
| 并发连接 | 2000 台稳定 ≥ 30 分钟，进程内存 < 512MB |
| 并发充电 | 1000 台，遥测端到端 p99 < 1s（帧到达 → 库可查） |
| 重连风暴 | 进程重启后 2000 台 60 秒内全部恢复在线 |
| 明细完整性 | 丢弃计数可解释；快照与聚合零丢失 |

## 理由

- 预算表明瓶颈不在吞吐而在故障路径；把设计力气花在「重启后 60 秒恢复」「缓冲满时丢什么」这类边界上，比堆吞吐优化有效。
- 明细分级丢弃是明确的价值取舍：遥测明细的用途是曲线展示与对账，秒级窗口的丢失对两者均无害（快照保证实时读、聚合保证曲线），换取的是 DB 写入路径永远不被设备风暴打穿。

## 后果

**正面**：容量验收可量化、可复现（批量模拟器 + 加速参数）；发布重启的设备断连成为常规操作而非事故。

**负面与对策**：
- 崩溃丢 ≤200ms 明细 → ADR 明示该取舍；聚合可由心跳重算，写入运维手册。
- 单实例即单点：进程重启设备自动重连（协议内建），HTTP 侧约秒级不可用 → 接受；多实例需要会话亲和（内存快照不共享），**拆分判据**：稳定运行中 CPU 持续 > 60% 或连接数逼近 10 倍目标（2 万台）。届时拆法：设备接入层独立为有状态服务（会话按设备号哈希分片），业务 HTTP 无状态可任意水平扩展——记此判据不写代码。
- 内存快照是权威实时数据源，会话表误清理会导致实时读缺数 → 快照缺失时回退查 DB（最近一条明细/聚合），降级路径有测试。

## 被否掉的替代方案

- **每帧同步落库（旧版行为）**：写放大无收益（67 行/秒本可直写），但失去崩溃窗口控制与批量摊销，且实时读与持久化耦合。
- **预置多实例/分片架构**：目标容量余量三个数量级，为不存在的规模付永久的运维与一致性复杂度。
