# Domain Docs

工程类技能在探索本仓库代码时应如何消费领域文档。

## 探索前先读

- 仓库根目录的 **`GLOSSARY.md`**（尚不存在则静默跳过，不要提示补建；`/domain-modeling` 技能会在术语真正落定时惰性创建）
- **`docs/blueprint.md`**：架构基准——已定架构事实（F1–F10）、终态目录树、crate 依赖规则、域 crate 内部模板。实施与蓝图冲突时，当场在其偏离登记表记一行，不要静默偏离

## 文件结构

单上下文仓库（本仓库即此形态）：

```text
/
├── GLOSSARY.md
├── AGENTS.md
├── CODING_STANDARDS.md
├── docs/
│   ├── blueprint.md          # 架构基准与实施计划
│   ├── operations.md         # 运行与数据维护
│   └── agents/
└── backend/
```

## 使用术语表的词汇

输出涉及领域概念时（议题标题、重构提案、假设、测试命名），使用 `GLOSSARY.md` 定义的术语；不要漂移到术语表明确避免的同义词。

如果所需概念尚不在术语表中，这是一个信号：要么你在发明项目不用的语言（请重新考虑），要么存在真实缺口（记录下来交给 `/domain-modeling` 处理）。

## 标记架构冲突

如果你的产出与蓝图的已定事实（F1–F10）或依赖规则矛盾，显式指出而不是静默覆盖，例如：

> 与蓝图 F3（事件事务内写入 + 进程内投递）矛盾，但值得重开讨论，因为……
