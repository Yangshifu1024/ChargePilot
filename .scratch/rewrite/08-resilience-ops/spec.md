# 阶段 08 · 兜底收口与运维能力

Status: ready-for-agent

## Problem Statement

各业务阶段的兜底扫描与周期任务分散落地，缺少统一收口与故障注入验证；运维缺少诊断入口，进程内部健康（队列深度、扫描滞后、循环存活）不可见。

## Solution

收口全部兜底扫描与周期 task 的统一运行框架，交付 admin 诊断接口，完成四类故障注入的真库验证——这是「事件驱动重构」风险的对冲阶段。

## User Stories

1. 作为运维者，我想在一个诊断接口看到全部后台循环的状态（最近运行、耗时、滞后、存活），所以不看日志也能判断系统健康。
2. 作为运维者，我想手动触发某个兜底扫描（诊断接口，带审计），所以补数不靠重启。
3. 作为开发者，我想让每个兜底扫描有统一的滞后指标与告警阈值位，所以扫描失速会先于用户感知被看见。
4. 作为开发者，我想验证「设备回执迟到」场景最终一致（状态机经兜底推进到正确状态），所以不惧慢设备。
5. 作为开发者，我想验证「事件丢失/投递器故障」场景（重启后 pending 事件重放、兜底接管），所以 at-least-once 名副其实。
6. 作为开发者，我想验证「进程重启」场景（在途状态收敛、无孤儿命令、无重复入账），所以发布安全。
7. 作为开发者，我想验证「遥测缓冲满」场景（明细丢弃计数、快照与聚合完好），所以分级语义被测试固化。
8. 作为运维者，我想让全部周期任务（导出清理、同步历史清理、会话清理等）有统一的取消与等待语义，所以停机序列完整。

## Implementation Decisions

- 兜底扫描统一框架：约 30s 固定间隔、每域注册自己的扫描器（启动意图超时、命令无回执、结束事件未处理、计费批次到期、退款意图超时、投递失败重试）；统一滞后指标与「最近运行」内存态。
- 诊断接口挂 admin 鉴权 + 操作审计；返回各扫描器状态与队列深度快照。
- 周期任务清单收口：导出清理（每小时）、同步历史清理（每小时）、会话与 MFA 过期（Redis 自管，仅观测）、批量冲刷（200ms）——全部纳入统一取消/等待框架。
- 故障注入测试基建：真库 + 真实时钟推进（可注入时钟推进超时场景）；每类场景一条端到端断言（HTTP 出口 + 库中最终行）。

## Testing Decisions

- 本阶段验收主体就是测试：四类注入场景（回执迟到、事件丢失、进程重启、缓冲满）各一条真库端到端断言，挂主缝与辅缝 3。
- 诊断接口行为：未鉴权拒绝、鉴权后返回结构与指标一致性（与 `/metrics` 交叉核对）。
- 停机：注册 N 个慢循环时 SIGTERM 后全部 join 再关池，有超时上限。

## Out of Scope

告警外发（邮件/webhook 通知，旧版亦无）；多实例下的扫描分片（单实例设计，ADR 005）。

## Further Notes
