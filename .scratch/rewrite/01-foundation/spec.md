# 阶段 01 · 平台地基

Status: ready-for-agent

## Problem Statement

骨架之上没有任何地基：没有配置加载与校验、没有日志与请求追踪、没有错误码表与响应信封、没有 ID 分配、没有事件投递能力、没有指标与优雅停机框架。业务模块无法开工。

## Solution

交付 `platform`、`storage`、`events` 三个 crate 的完整能力与 G6 观测指标框架，使后续每个业务阶段只写业务本身。

## User Stories

1. 作为开发者，我想用带 required 校验与取值校验的 env 配置加载，所以缺配置、密钥长度不足在启动时即失败而不是运行时。
2. 作为运维者，我想让日志带 request_id 并贯通一次请求的全部处理，所以排查问题不用靠时间戳猜关联。
3. 作为开发者，我想有统一错误码表（1xxx 凭证 / 2xxx 冲突 / 5xxx 故障）到 HTTP 信封的映射，所以各业务模块不各自发明错误响应。
4. 作为开发者，我想从号段分配器拿 ID（内存号段 + 水位 CAS 持久化），所以高并发写入不再排队在一个全局行锁上。
5. 作为开发者，我想在资金写入路径选择「取号与业务同事务提交」的强一致选项，所以关键单据不出现崩溃跳号可见。
6. 作为开发者，我想把领域事件写入同事务并由投递器异步送达处理器，失败指数退避，所以事件不丢也不阻塞业务事务。
7. 作为运维者，我想在 `/metrics` 看到连接数、事件投递延迟、兜底滞后等指标（即使部分恒为零），所以容量验收有统一的数据来源。
8. 作为运维者，我想让进程收到 SIGTERM 后：停止接活 → 等待在途任务与投递器冲刷 → 再关连接池，所以发布不丢数据。
9. 作为开发者，我想有 JWT 签发校验、bcrypt、TOTP、刷新令牌编码与 Lua 轮换/注销脚本的平台能力，所以登录体系（阶段 02）只写流程不写密码学。

## Implementation Decisions

- 配置：env 加载，required/取值/密钥长度校验语义照搬旧版（`PAYMENT_MODE` 三态、`JWT_SECRET` ≥32 字节、`WECHAT_APIV3_KEY` 32 字节等）。
- 信封与错误码：中间件统一 `{code, message, data, request_id}`；错误 enum 全局唯一定义。
- 号段分配器（[ADR 003](../../../docs/adr/003-segment-id.md)）：号段 500；水位 CAS（`UPDATE ... WHERE 水位 = 旧值`）；水位未落库且号段耗尽时阻塞等待，不得静默重用；强一致路径供资金场景显式选择。
- 事件投递器（[ADR 002](../../../docs/adr/002-event-driven-state-machine.md)）：同事务写 `domain_event`；提交后异步 task 逐条投递；失败退避 `1 << min(retry, 8)` 秒；投递器本身接受停机取消并等待在途事件处理完。
- 指标框架（[ADR 005](../../../docs/adr/005-capacity-boundary.md) G6 清单）：连接数、充电数、帧速率、批量缓冲深度与丢弃计数、事件投递延迟、兜底扫描滞后、DB 批量大小——本阶段先注册并暴露，业务阶段填充。
- 平台能力：jsonwebtoken（HS256 双 kind）、bcrypt、TOTP（30s/6 位/±1 步）、刷新令牌 `RT_/ART_` 编码 + SHA-256 摘要 + Redis Lua（保留 32 旧摘要、KEEPTTL）——Lua 脚本从旧版原样移植。
- storage：单连接池 + 通用 dbutil（唯一键冲突识别 1062、UTC 月首日、LIKE 转义）。

## Testing Decisions

- 号段：并发取号不重复、崩溃模拟（号段未持久化）后不回拨、水位 CAS 冲突重试——真库测试。
- 事件投递：处理器注入失败后按退避重试直至成功；进程重启后 pending 事件被重新投递（at-least-once）——真库测试。
- 停机时序：注入慢处理器，断言「先任务后连接池」的顺序与超时上限——辅缝 3。
- Lua 轮换：对 Redis 真实执行轮换/注销，断言旧摘要保留行为。
- 全部经主缝或辅缝 3 断言，不 mock 内部协作对象。

## Out of Scope

任何业务路由注册；微信支付封装（阶段 04）；网关 TCP 能力。

## Further Notes

指标恒为零是预期：本阶段交付的是「有指标可看」，数字来自后续阶段。
