# 阶段 03 · 计费方案与设备站点

Status: ready-for-agent

## Problem Statement

没有计费方案就无法定价，没有设备与站点台账就无法下单。后台基础数据（计费方案、站点、设备、厂商、导入、故障、告警）与 C 端站点浏览能力缺失。

## Solution

交付 pricing 域（方案/规则/发布/继承/计量匹配）与 device 域（站点/设备台账/厂商/批量导入/故障工单/告警同步）全量路由，admin 静态资源开始由后端服务。

## User Stories

1. 作为运营人员，我想创建计费模板并配置分时段费率（尖/平/谷等），所以不同场景能差异化定价。
2. 作为运营人员，我想把模板发布为对设备生效的方案并支持继承（站点级覆盖设备级），所以批量管理不必逐台设置。
3. 作为运营人员，我想维护站点（地址、坐标、营业时间）与设备台账，所以用户端能展示准确的站点信息。
4. 作为运营人员，我想批量导入设备（一批 ≤100 台）并自动向设备开通，所以千台规模接入不是手工活。
5. 作为运营人员，我想管理厂商及其接入参数，所以新厂商接入有配置入口。
6. 作为运营人员，我想看到用户提交的故障工单并流转（受理/处理/关闭），所以报修有闭环。
7. 作为运营人员，我想让设备告警自动同步成告警事件并可认领处理，所以故障不被淹没。
8. 作为充电用户，我想按距离查附近站点并看站点详情（设备与端口空闲情况、计费方案），所以能决定去哪充电。
9. 作为运营人员，我想看设备实时状态摘要（心跳/信号/端口占用），所以远程掌握设备面。
10. 作为开发者，我想设备开通落库与 TCP 下发解耦（设备离线时开通，上线后同步），所以导入不依赖设备在线。

## Implementation Decisions

- pricing 三层模型（模板 → 发布方案 → 计量匹配）语义照搬旧版；分时段费率解析含跨零点与默认费率回退（`DEFAULT_TIME_OF_USE_JSON`）。
- 表归属定案依阶段 00 设计稿：站点/设备台账/厂商/导入任务属 device 域写；连接会话/遥测/命令属 gateway-runtime 写——本阶段 device 域只写自己的表，运行时表留待阶段 06。
- 设备导入：受理（建任务）→ 执行（批量开通落库 + 幂等 `device_provision`）→ 状态回写；开通与 TCP 同步的桥接在阶段 06 补全（本阶段设备离线也能导入成功）。
- 告警同步：故障事件 → 告警事件生成与恢复判定（心跳水位），本阶段消费方为后台页面；事件来源（设备上报）在阶段 06 接通。
- 静态服务：`/admin/*` serve 构建产物 + SPA fallback（history 路由）；构建产物由 Dockerfile 注入，开发期可用本地目录配置。
- C 端站点查询为公开接口（无登录），注意与私有接口的中间件分组。

## Testing Decisions

- 主缝真库集成：模板→发布→覆盖继承链路；导入受理→执行→幂等重放（重复导入不重复建档）；故障工单流转状态机；告警生成/恢复。
- 静态服务：SPA fallback 对 `/admin/任意路径` 返回 index.html；未构建产物时返回明确 5xxx 而非崩溃。
- 计费方案解析（时段切分、跨零点）为纯规则，直接单测（domain 层），并用旧版同输入差分对照。
- 坐标距离计算与附近排序的边界（空坐标、越界）有测试。

## Out of Scope

设备 TCP 连接、遥测、远程启停（阶段 06）；下单扣费（阶段 04）；前端页面的新增或改版（契约修剪随阶段 09 统一回归）。

## Further Notes

导入的「开通后 TCP 同步」依赖 gateway-runtime，本阶段接口留缝（开通记录带待同步标记），阶段 06 消费。
