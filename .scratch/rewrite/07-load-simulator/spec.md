# 阶段 07 · 批量模拟器与压测

Status: ready-for-agent

## Problem Statement

没有能在笔记本上模拟大规模设备的工具：旧版 TUI 模拟器一次只能跑一台，容量目标（2000 连接 / 1000 充电）无法在开发期验证，只能上线见真章。

## Solution

交付 headless 批量模拟器：一条命令拉起 N 台虚拟设备跑完整协议生命周期，支持心跳加速与充电比例参数，输出运行统计，作为容量验收的加载源。

## User Stories

1. 作为开发者，我想一条命令模拟 2000 台设备注册上线并保持心跳，所以连接层容量可日常验证。
2. 作为开发者，我想指定充电台数（如 1000），所以充电负载比例可控。
3. 作为开发者，我想把心跳/计量间隔按倍率加速（如 15 倍），所以几分钟打满相当于数小时的真实负载。
4. 作为开发者，我想让虚拟设备跑完整生命周期（注册→命令启停→计量上报→结束订单→故障注入），所以压测覆盖协议全路径而不只是心跳。
5. 作为开发者，我想在压测中按比例注入异常（迟到回执、静默断连、重连风暴），所以故障路径也有负载验证。
6. 作为运维者，我想看模拟器输出的统计摘要（发送帧数、应答率、错误分类），所以加载强度可解释。
7. 作为开发者，我想让模拟器可脚本化（无 TUI、退出码反映成功失败），所以能进自动化验收流程。

## Implementation Decisions

- 形态：`app` 的独立子命令（`simulator-batch`），参数 `--devices` / `--charging` / `--speedup` / `--target-addr` / `--duration` / `--chaos-ratio`。
- 协议复用：直接使用 `protocol-dc589` 帧层（同一实现即契约），不另写协议副本。
- 并发模型：每虚拟设备一个 tokio task，共享一个连接池大小的 TCP 连接数；会话 ID 与设备号生成确定性可复现（种子参数）。
- 加速实现：按 `speedup` 缩放心跳/计量定时器，不改变协议字节内容。
- 异常注入：`--chaos-ratio` 控制迟到应答、半开连接、注册风暴重放三类行为。
- 本工具是测试工具链，不属于生产二进制的服务路径（但随同一镜像交付便于现场排障）。

## Testing Decisions

- 自身行为：种子确定性（同种子同帧序列抽样比对）、加速参数对定时器间隔的纯逻辑单测。
- 集成：对开发栈跑 2000 注册 / 1000 充电（加速档）冒烟通过，作为本阶段验收；全量容量指标断言在阶段 10 执行。
- 输出统计与 `/metrics` 交叉核对（发送帧数与网关帧速率指标一致量级）。

## Out of Scope

TUI 交互界面（旧版 Go TUI 模拟器保留在旧仓库作单台调试用）；性能调优本身（本阶段只交付加载工具，优化在阶段 10 验收驱动）。

## Further Notes

模拟器协议实现与网关共用帧层，天然构成互逆测试——这使黄金样本之外的协议覆盖免费获得。
