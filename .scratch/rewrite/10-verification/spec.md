# 阶段 10 · 全量验证与容量验收

Status: ready-for-agent

## Problem Statement

各阶段有各自的阶段验收，但没有一次全量关闸：契约快照、E2E 闭环、容量四项硬指标没有在同一构建上完整跑过并出报告，不能宣布重写完成。

## Solution

在阶段 09 的镜像与全栈上执行全部验收闸门，产出《重写验收报告》：功能验收五项 + 容量验收四项，全部以可复现命令与指标数据说话。

## User Stories

1. 作为验收者，我想契约层全绿（serde 序列化 + OpenAPI 路由快照，基准为阶段 00 冻结的新 OpenAPI），所以对外形状有权威断言。
2. 作为验收者，我想资金域差分对照报告（同输入新旧两版输出一致），所以计费分位无漂移被数据证明。
3. 作为验收者，我想资金链路与并发/幂等真库集成全绿，所以资金安全不是口头承诺。
4. 作为验收者，我想 E2E 全链路闭环（模拟器：注册→扫码→启动→计量→停止→结算→退款），所以真实协议路径贯通。
5. 作为验收者，我想看到 2000 连接稳定 30 分钟且进程内存 <512MB，所以连接层容量达标。
6. 作为验收者，我想看到 1000 并发充电下遥测端到端 p99 <1s（帧到达→库可查），所以数据管道达标。
7. 作为验收者，我想看到进程重启后 2000 台 60 秒内全部恢复在线，所以发布窗口可控。
8. 作为验收者，我想看到缓冲丢弃计数可解释且快照/聚合零丢失，所以分级语义在真实负载下成立。
9. 作为维护者，我想验收报告中每项附复现命令与环境说明，所以任何人可重跑验证。

## Implementation Decisions

- 验收基线 = 阶段 09 镜像 + 全栈 compose + 批量模拟器（加速档打满目标负载）。
- 差分对照执行方法：旧仓库只读 checkout + 固定输入集（计费/退款/卡扣用例文件），两边各自运行、输出比对；输入集与结果入库归档。
- 容量采集：`/metrics` 拉取 + 容器内存观测 + 模拟器统计三方交叉；报告含原始数据。
- 报告模板固化到 `docs/`，验收命令脚本化（一条命令跑全部功能闸门）。

## Testing Decisions

- 本阶段即测试执行与报告，不新增被测代码；验收中发现缺陷回对应阶段 spec 的范围修复并复跑该阶段验收 + 本阶段全量。
- 通过标准：功能五项全绿 + 容量四项达标（[ADR 005](../../../docs/adr/005-capacity-boundary.md) 硬指标）。

## Out of Scope

上线前清单（真实微信商户联调、weapp 真机发布、TLS/域名）；性能进一步调优（验收不达标时先归因：属缺陷回各阶段修，属预算修正走 ADR 修订）。
