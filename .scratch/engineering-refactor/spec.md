# ChargePilot 工程结构重构（二期）规格

Status: ready-for-agent
日期：2026-11-14
上游基准：[docs/refactor-plan.md](../../docs/refactor-plan.md)（诊断证据、批次表、评审记录以该文档为准，本文是其可执行规格化）
红线：对外行为、HTTP 信封与错误码数值、微信回调契约、DC589 协议、计费算法、行锁/幂等语义、DB ENUM 字面量——全部不变。

## Problem Statement

ChargePilot 完成了从 Go 多服务到 Rust 单体的一期重写，但开发者每天仍要在四类摩擦上付费：

1. **看不懂结构**：代码组织横跨三种范式——全部 HTTP 处理器按 admin/user 横切集中在一个 crate（一个财务文件同时调三个业务域），业务 crate 内部服务与 SQL 混写无分层，领域层只覆盖少数域。评审者无法回答「这个改动该落在哪」，新人无法建立心智模型。
2. **类型不严**：数据库有 63 个 ENUM 状态列，代码里却是常量串容器、字符串新类型与裸字面量三种退化写法；界限值（最大充电分钟数、口令长度、分页上界）以内联魔法数重复散布；配置绕过统一加载点被各模块直读环境变量；错误类型各域自造、同一契约码有两套表达。
3. **门禁缺失**：日常检查只有格式化加测试两步，没有 clippy、没有 lint 配置、没有依赖审计；任何警告、任何绕过约定的写法都不会被机器拦住。
4. **测试不可信**：约 78% 测试代码在环境变量缺失时被静默跳过且显示为通过——资金、幂等、设备闭环主缝在日常检查中实际执行率为零；同时存在无断言的伪有效测试、跨文件大面积重复的装配辅助代码，以及两类互不互斥的并发锁。

## Solution

以「垂直域为主轴的混合式」统一结构（12 个业务域 crate 为第一公民、单一薄聚合 API 层按域分目录、少量共享 crate），用 Rust 枚举与值对象替换全部字符串词表与魔法数，把配置、错误码收编进统一入口并配机器禁令，建立三层门禁（本地 check、真库集成门禁、契约快照），并完成一次以「删伪有效、治静默跳过、去装配重复」为主题的测试治理。全程分 S0–S8 九个批次，每批独立验收、按级联组回滚，对外行为与数据库语义零变化。详细设计、证据与五视角评审记录见上游基准文档。

## User Stories

1. 作为后端开发者，我想让每个业务改动有唯一的落点判断规则（先问业务域、再问是否纯规则、最后才轮到 HTTP 层），所以我不再需要在多个候选位置之间犹豫。
2. 作为后端开发者，我想让每个业务域 crate 内部有固定模板（门面/错误/服务/仓储），所以打开任何一个域 crate 都能预判代码的物理位置。
3. 作为后端开发者，我想让 SQL 只出现在各域的仓储模块里，所以审查资金写入时不必通读整文件去确认没有隐藏的表操作。
4. 作为代码评审者，我想让 HTTP 处理器目录按业务域组织（每域 admin/user 两个薄门面），所以评审一个财务端点改动时不必在跨域大文件里找上下文。
5. 作为代码评审者，我想让跨 crate 依赖即清单（Cargo 依赖声明就是域间依赖的真相源并附业务理由），所以依赖方向违规在编译期暴露而不是靠人肉记忆。
6. 作为代码评审者，我想让状态取值的合法性由编译器保证（match 穷尽、通配分支被禁止），所以拼错状态串这类错误在编译时就失败。
7. 作为后端开发者，我想让数据库 ENUM 列与 Rust 枚举一一对应且字面量被对照测试锁定，所以改表或改码时任何一侧漂移都会立刻被测试抓住。
8. 作为后端开发者，我想让设备上报的未知停止原因原样保留（透明透传而非结构化包装），所以既有 JSON 证据的逐字节幂等比对不被破坏。
9. 作为前端开发者，我想让所有枚举的对外字面量与错误码数值在重构前后逐字节一致，所以二期合入后前端与小程序无需任何配合改动。
10. 作为后端开发者，我想让界限值集中在一处常量模块且逐条注明旧版出处，所以「最大充电时长到底是多少」这类问题有唯一答案。
11. 作为后端开发者，我想让分页校验收敛为参数化校验器但保留 C 端与后台的双轨上界，所以消重复的同时不改变任何一端的行为。
12. 作为运维部署者，我想让全部环境变量由统一配置结构一次加载，所以排查配置问题只需看一个文件。
13. 作为后端开发者，我想让业务模块彻底不读环境变量（机器禁令拦截），所以「某行为受哪个变量影响」永远可回答。
14. 作为部署者，我想让支付/登录模式等枚举型配置在启动时即校验失败，所以非法配置不会带病运行到请求时刻。
15. 作为后端开发者，我想让错误类型统一为派生式领域错误且存储错误的语义分类（如唯一键冲突）被保留，所以下游错误匹配不因重构静默失效。
16. 作为后端开发者，我想让旧版契约错误码（含一码多 HTTP 状态的码）收编进统一的码表与映射层，所以同一契约不再有两套表达。
17. 作为后端开发者，我想让 HTTP 层的全局依赖对象拆成按域分组、装配期必达的子状态，所以「某服务未装配」从运行期惊喜变成编译期约束。
18. 作为开发者，我想让 clippy 的正确性/可疑/性能组与通配枚举分支检查成为失败级门禁，所以低级错误进不了主干。
19. 作为开发者，我想让直接读环境变量成为 clippy 禁止项（白名单豁免登记），所以配置收编不会随时间倒退。
20. 作为维护者，我想让真库集成测试显式标记为忽略并在专门任务里全量运行，所以「全绿」恢复含义——要么真跑过，要么明确显示多少被忽略。
21. 作为测试维护者，我想让集成测试的连接失败被判定为失败而非跳过，所以环境故障不会被误读为测试通过。
22. 作为测试维护者，我想删掉无断言与常量考据型测试并以行为测试替代，所以测试数量下降的同时守护能力上升。
23. 作为测试维护者，我想把 21 个测试文件重复的装配与请求辅助代码收敛到共享支撑模块，所以新增一条流测试不再复制两三百行脚手架。
24. 作为测试维护者，我想让并发测试统一为跨进程互斥的端口锁，所以资金/频次类断言在并行执行下依然稳定。
25. 作为测试维护者，我想让测试辅助设计预知目标状态形态（构建器模式），所以结构重排批次不需要把共享辅助代码推倒重写。
26. 作为开发者，我想让路由集合与信封形状有契约快照测试（手写清单加探测断言），所以大规模文件移动有机器护栏而不依赖人工核对。
27. 作为开发者，我想让资金关键判定（计费分段守恒）有直测的纯函数单测，所以它不依赖平时不运行的真库流测试。
28. 作为部署者，我想让前端产物编译期嵌入二进制并隔离在独立叶子 crate，所以镜像内二进制与页面版本永远一致且改前端不会重编整个后端。
29. 作为部署者，我想让镜像构建带版本号冒烟自检，所以坏镜像在构建阶段即暴露。
30. 作为维护者，我想让每批重构独立成提交且回滚单位与依赖关系显式登记，所以任何一批出问题都能按级联组干净回退。
31. 作为维护者，我想让微信支付回调端点的接线状态在开工前被核实并登记为红线对象，所以后续接线路由时契约保护有明确对象。
32. 作为新加入的维护者，我想让方案的诊断证据、评审结论与修订记录集中可追溯，所以理解「为什么这样设计」不需要考古会话记录。
33. 作为 AFK 代理，我想让每个批次的验收标准机器可执行（检查三件套、真库集成、契约快照），所以无人值守执行的结果判定不含糊。
34. 作为项目负责人，我想让与并行修复会话的冲突面在每批开工前例行核对，所以结构重构与缺陷修复互不踩踏。

## Implementation Decisions

以下为已裁决的实现决策（裁决依据与备选方案的完整论证见上游基准文档第三节、四节）：

- **结构范式**：垂直域为主轴的混合式。第一级拆分是业务域 crate（12 个，保持现有边界），共享 crate 收敛为领域词表、平台通用能力、存储、协议两层、事件、装配入口；不按层建 crate（层是 crate 内的目录）。
- **HTTP 层归宿（D1，评审确认）**：保留单一薄聚合 API crate，内部按「域目录 × admin/user 门面」重排；处理器只做鉴权提取、入参绑定、调域服务、信封输出。不把处理器下沉进域 crate（避免 12 个域引入 HTTP 框架依赖）。
- **域 crate 模板**：门面（只导出服务类型与构造，禁止导出仓储）、领域错误、服务层（按子域分文件）、仓储层（SQL 唯一归所）。约八百行以下的域可平铺为两个文件。
- **依赖规则**：领域词表零依赖；平台/存储/协议不依赖业务；域 crate 之间显式声明并注释业务理由；聚合 API 层是唯一允许依赖业务域的横切 crate 且按需声明；装配根是唯一经统一配置读环境的进程位置。现行跨域依赖经评审核对为有向无环，逐条入册。
- **枚举化范式（D4，评审核实）**：数据库 ENUM 列对应 Rust 枚举，用 sqlx 的类型派生（MySQL 字符串枚举原生支持，无需手写编解码宏）；sqlx 与 serde 各自的重命名配置必须成对书写并由字面量对照测试锁定。三条未知值策略：数据库到 Rust 方向严格失败（即 schema 漂移报警）；设备/外部上报方向保留原值并以透明 serde 表示（不破坏 JSON 逐字节幂等往返）；API 入参方向解析失败返回参数错误（与现行为一致）。
- **枚举化前置设计物**：先产出「63 列 ENUM ↔ 现有字符串类型 ↔ 域归属」三方对照表，显式拆分跨表混装的支付状态类型（支付单六值与订单支付轴四值是两个词表），再动代码。设备故障类字面量持久化在 JSON 列，不走数据库枚举范式。
- **词表归属修正**：在线卡状态归卡域（不归设备域）；支付意图状态与支付单状态分家后各有唯一属主；事件类别词表转为进程内枚举（数据库侧为无约束字符串，保持透传）。
- **魔法数**：全局界限值集中常量模块并注明旧版出处（旧版多处内联，无具名常量可引）；充值与退款的金额下界是两个不同的常量。
- **分页双轨（评审对旧版核实后的定论）**：C 端十万、后台一百万是旧版有意设计，维持双轨；校验收敛为携带上界的参数化校验器（用户态/管理态两个构造入口）；状态过滤的两种既有语义（静默降级与返回参数错误）按调用点保留，不顺手统一。
- **配置收编**：配置结构扩展为全量分组（含支付模式、登录模式两个枚举型配置），非法取值启动即失败并补断言测试；冻结环境变量清单与配置结构之间建立一致性测试（前提是全量配置落地，两件事同一次改动）；环境变量直读进 clippy 禁令，测试变量与压测命令行的数据库地址作为登记豁免。
- **错误体系**：各域错误统一定义式错误；存储错误收编为 sqlx 错误的派生变体并同步移除错误类型上无消费点的相等性派生；订单编号冲突的语义分类（数据库唯一键冲突到业务冲突的映射）必须保留，不得被纯派生替换；承载非数据库错误的 anyhow 形态不强行收编。契约码表补齐旧版缺口并以「显式状态覆盖」能力支持一码多 HTTP 状态；映射收编分两步——先收编三处既有映射枢纽与码表缺口，全部字面量调用点的全量收编归入域内模板批次。
- **依赖注入消解**：全局依赖对象拆为按域分组的最小句柄组（含数据库句柄），装配期必达、无可选字段；子状态经 axum 的 FromRef 提取（手写实现，不引入宏特性依赖）；各域装配逻辑上移到组合根。
- **静态资源（D2）**：前端双产物以 rust-embed 嵌入，各自隔离在依赖面最小的叶子 crate（不依赖平台 crate，所需值由装配根传参），允许本地缺失产物编译；SPA 回退逻辑随迁；部署形态变更记 ADR。
- **门禁配置**：rustc 警告即错误；clippy 的正确性/可疑/性能组与通配枚举分支为失败级，全部警告级，测试内解包豁免用原生开关落地；环境变量直读进 disallowed-methods；rustfmt 锁定行宽并预留 nightly 项；pedantic 与依赖审计（deny.toml）、CI、nextest 均列为缓引入或不引入（理由见上游基准 6.2 节）。
- **任务入口**：扩展现有 Node 任务脚本（新增 clippy、真库集成任务含库重建/清理选项、契约检查脚本接入），不引入 make/just 迁移。
- **批次与回滚**：S0 基线（含回调端点接线核实、契约快照生成、忽略标记落地）→ S1 门禁 → S2 测试基建 → S3 枚举化（八个子批，前置对照表）→ S3.5 可选状态机接线 → S4 常量配置 → S5 HTTP 重排 → S6 域内模板（含错误全量收编）→ S7 静态资源 → S8 收尾销项。回滚单位是级联组（金钱词表批被五个 crate 引用，单独回退必然级联），每批提交说明登记下游依赖；每批开工前例行核对与并行修复会话的冲突面。
- **工作量**：合计约 15–19 天（评审修正后的估算，四大隐性工作量为枚举化前置对照表、错误码全量收编定量、域内模板体量、门禁存量清零）。

## Testing Decisions

- **好测试的判据**：只测外部可观察行为（路由、信封、状态字面量、库中资金行），不测实现细节；删除任何一条现有断言前必须指明同路径的更强替代覆盖，指不出即撤回删除。
- **测试缝设计（用户已确认）**：唯一新增的缝是「契约缝」——手写路由清单常量加探测式断言（已知路径错方法得 405、未知路径得 404 信封，区分度成立）、信封代表 DTO 的序列化对照（代表清单按域生成，字段基线提炼自现有集成测试已逐字段断言的集合）、每个枚举的字面量对照（同时锁 serde 与 sqlx 两套配置的一致性）。其余全部复用现有缝：HTTP 主缝（路由构建函数加 oneshot，现有 26 个真库流测试所在）、纯函数缝（域黄金差分与内嵌单测）、编译期缝（trybuild 反例与 lint 门禁）、部署缝（仅新增镜像版本冒烟一行）。
- **运行门槛治理**：全部真库流测试静态标记忽略，日常检查的汇总行恒显通过数与忽略数；专门集成任务注入连接变量并以「包含忽略」方式全量运行；该轮中连接失败判失败；内嵌的脚本回归测试（红线级）一并纳入忽略治理。
- **删除/裁剪/加固清单**（逐条经审计与二次独立复核，对象均为具体测试，实施时以最新代码再复核）：删无断言与恒真的配置默认值测试；删两个环境变量清单考据测试（前提：一致性测试与未知变量告警的行为测试先行落地）；删真实 Redis 单次探活测试；裁剪与另一文件严格超集重复的计量核实场景（保留全仓独有的人工金额分支）；合并状态机可表达性测试并补上从未被调用的迁移方法调用；加固登录流测试中被丢弃的两处响应断言（旧令牌失效断言已存在，勿重复）。
- **补测清单**（与删除同批落地）：环境变量未知告警逻辑提为纯函数后直测四条语义；计费分段守恒判定提为纯函数后按四类输入直测；模式枚举配置的非法取值启动失败断言。
- **辅助代码治理**：共享支撑模块用构建器模式（默认最小装配，按需开启各域句柄），设计预知 S5 的目标状态形态；并发互斥统一为跨进程端口锁并论证种子隔离边界，锁语义变更写入批次验收；支撑模块须区分「跳过」与「失败」。
- **先例**：枚举字面量对照沿用现有错误码冻结测试的范式；信封对照的字段基线沿用现有财务流测试的逐字段断言集；枚举行为直接复用领域层黄金差分样本护航。

## Out of Scope

- 任何对外行为、契约、数据库 schema 与取值的变化（含分页上界的「顺手统一」——双轨是定论不是待办）。
- 微信支付回调端点的补接线（S0 只核实登记；接线属功能开发，另起工票）。
- CI 的实际启用（仓库当前无远端；门禁与工作流设计已备好，建远端后按上游文档 6.2 节落地）。
