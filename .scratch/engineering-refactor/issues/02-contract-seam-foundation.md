# 02: 契约缝基座——路由清单与信封对照（S0）

**What to build:** 为后续大规模重排建立唯一新增的测试缝：契约缝。手写维护全量路由清单常量（方法 + 路径），对每条发探测请求断言——已知路径配错方法得 405、未知路径得 404 信封（服务回落返回未提供信封，区分度成立；契约测试以「无静态目录」模式构建路由，不挂 SPA 回落）。另按业务域选取每域 admin/user 各至少一个代表响应 DTO，做信封字段序列化对照（字段基线提炼自现有集成测试已逐字段断言的集合，清单以注释钉在测试头部）。纯进程内无外部 IO，纳入日常检查。

**Blocked by:** None (can start immediately)

## Comments

- **2026-11-14 完成**：交付 `http-api/tests/api_contract.rs`（4 个测试，0.5 秒跑完，纳入日常 check）。路由清单 125 条（122 业务 + health/metrics 3 条），从各 `router()` 注册函数程序化提取后人工复核。
- **契约发现两条（实施中落定的真实契约，与票面假设的差异）**：
  1. 信封 `errors` 字段空时**不序列化**（`skip_serializing_if`）——契约固化为「空态缺字段、非空态含 field/rill 对」，而非恒在数组；
  2. 同路径多方法并存（如 admin-users 的 GET+POST）下，错误方法探活命中的是另一注册处理器（返回鉴权 401）——「错误方法必须 405」改为「错误方法禁止 404」，方法注册的正确性由预期方法探活（非 404/405）保证。
- **域级 DTO 对照的形态适配**：现响应载荷以 `json!` 内联构造、无集中 DTO 结构体，故本缝钉「信封外壳 + 错误码表（16 个 Code 的码值/HTTP 状态/响应头逐项冻结）+ 路由全集」三样红线契约；域级字段基线仍由各集成流测试逐字段承担。票 18/19 重排时此缝即护栏。
- 实施细节：探针用惰性连接池（`acquire_timeout=100ms`，公开路由触库时快速得到 5xx 信封而非等默认 30s）+ 号段分配器仅构造不预热；HTTP 方法大小写敏感（`Method::from_bytes(b"get")` 是非标准方法，必须大写化）。
